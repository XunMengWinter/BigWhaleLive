# AI 自主聊天直播间 MVP 方案

整理日期：2026-11-08  
来源：AI直播间方案分享对话（分享链接已移除）。

本项目实现一个能够自主聊天并回应观众弹幕的 AI 虚拟主播。用户在原对话中明确选择了 B站首发和 Live2D 二次元角色；第一版以 Mac mini 本地运行为目标，采用 Python Agent、Web 舞台与 OBS 的组合。

本文保留分享对话中的需求和历史方案，不作为当前接口或操作手册。对应代码未导入，不能直接启动。当前实施以 [架构](architecture.md)、[API 合同](api-contract.md)、[运行配置](runtime-config.md) 和 [验收用例](acceptance.md) 为准，协作遵循 [AGENTS.md](../AGENTS.md)，实际进度维护在 [status.md](status.md)。

2026-11-08 实施修订：用户已指定当前形象直接采用 dsh-pet 原版大肥鱼透明动画；默认采用离线字幕演示，显式配置真实服务；启动为暂停状态；B站改走官方开放平台，不再安装已停止维护的 bilibili-api-python。下文旧配置与优先级示例仅用于保留来源语义。

## 1. 产品目标与功能范围

直播间安静时，AI 可以主动讲故事、吐槽、提问或延续话题；观众发送弹幕后，AI 判断是否需要回复，并结合当前聊天上下文自然接话。角色在说话时配合嘴型和表情，舞台同步显示字幕。

### 第一版 MVP

| 能力 | 第一版方案 |
| --- | --- |
| 自主聊天 | 自动选择话题，按状态与节奏生成台词 |
| 弹幕回复 | 先支持本地模拟弹幕，再通过可替换适配器接入 B站 |
| 大模型 | 使用 OpenAI 兼容接口，服务商和模型通过配置指定 |
| 演示模式 | 未配置模型密钥时，使用预设文案模拟 Agent 行为 |
| 语音合成 | Edge TTS，默认音色为 `zh-CN-XiaoxiaoNeural` |
| 角色展示 | Live2D Cubism 3/4 模型；无模型时使用 CSS 演示角色 |
| 嘴型 | 原 MVP 采用近似开合，后续再升级音频振幅同步 |
| 字幕 | 舞台实时显示 AI 台词 |
| 控制台 | 本地发送模拟弹幕，验证互动链路 |
| 直播输出 | OBS 浏览器来源加载舞台页面 |

### 后续阶段

- 礼物、点赞事件及感谢语、表情和动作联动。
- 工资进度条、倒计时、互动小游戏。
- 更精细的音频驱动嘴型、情绪和动作表现。
- 抖音适配，以及独立虚拟主播软件形态。

第一版不引入数据库、Redis、Docker，也不要求部署云服务器。原始讨论曾列出 SQLite、CosyVoice 等可选方案，后续 MVP 方案收敛为无数据库与 Edge TTS。

## 2. 技术架构

```text
B站直播弹幕 / 本地模拟弹幕
              │
              ▼
Python + FastAPI 核心服务
  ├─ 平台适配与事件接收
  ├─ 弹幕过滤、用户识别、优先级队列
  ├─ Agent 状态机与短期聊天记忆
  ├─ LLM 台词、情绪、动作生成
  ├─ TTS 音频合成
  └─ WebSocket 事件推送
              │
              ▼
Web 舞台：PixiJS + Live2D
  ├─ 角色、背景与待机动画
  ├─ 音频播放与嘴型
  └─ 字幕、表情与动作
              │
              ▼
OBS Studio → B站直播间
```

| 模块 | 原方案选型 | 职责与边界 |
| --- | --- | --- |
| 核心服务 | Python、FastAPI、asyncio | 调度 Agent、接收互动事件、提供页面与接口 |
| 实时通信 | WebSocket | 后端向舞台推送台词、音频和角色事件 |
| AI 生成 | OpenAI 兼容 LLM API | 生成自主话题与弹幕回复 |
| 语音 | Edge TTS | 将台词转换为可播放音频 |
| 舞台渲染 | PixiJS 6、pixi-live2d-display | 展示 Cubism 3/4 角色并驱动表现 |
| 运行库 | Live2D Cubism Core | 单独准备所需运行库 |
| B站适配 | 原提案为 bilibili-api-python，已废止 | 当前改为官方开放平台适配，见架构 |
| 推流 | OBS Studio | 合成舞台、字幕和音频并推流 |

原方案参考了 [pixi-live2d-display](https://github.com/guansss/pixi-live2d-display)。具体依赖版本、模型兼容性和运行库使用条件，在实现时确认。

## 3. Agent 互动逻辑

### 状态与切换

```text
空闲 → 自主聊天中 → 空闲
           │
           └─ 收到值得回复的弹幕 → 回复弹幕中 → 恢复聊天 → 空闲
```

状态机负责决定何时发言、何时回复，以及回复后如何回到原话题。避免只按固定间隔重复调用大模型。

1. 直播间安静时，周期性判断是否需要主动发言，保留自然停顿。
2. 弹幕进入过滤与筛选流程，避免垃圾信息将话题带偏。
3. TTS 播放期间，新弹幕进入队列；重要事件可按优先级打断当前发言。
4. 保留最近对话及摘要，让 AI 记住当前话题和近期互动。
5. 每次生成结构化结果，将台词与情绪、动作一起交给舞台处理。

原对话给出的结构化输出示例：

```json
{
  "type": "reply",
  "text": "你怎么又来抓我摸鱼啦！",
  "emotion": "shy",
  "action": "shake_head",
  "priority": 8
}
```

该结构仅保留原输出意图。当前协议已在 API 合同定义，kind 和优先级由后端赋值，LLM 只输出台词、情绪和动作；普通弹幕不抢占当前发言。阶段 1A/1B 已实现本地调度、演示与真实台词、真实语音，当前角色按用户要求使用 dsh-pet 原版动画。

## 4. 平台接入边界

首发平台为 B站。推流能力与弹幕读取能力分开处理，OBS 能推流并不代表后端已经获得互动消息。

- **官方接入方向**：原方案指向 [B站直播开放平台](https://open-live.bilibili.com/)，开发者资格和具体消息权限需在接入时确认。
- **已废止的实验适配**：原方案曾使用 `bilibili-api-python` 与 `BILI_ROOM_ID`；其[上游已停止维护并归档](https://github.com/Nemo2011/bilibili-api)，当前不再采用。
- **模块隔离**：B站接入做成可替换适配器，先用模拟事件验证 Agent，降低平台接入对核心链路的影响。

原讨论还参考了 [bilive-danmaku](https://github.com/Beats0/bilive-danmaku)，将其作为 Electron 弹幕工具参考，而非直接作为 Python 服务依赖。

抖音属于后续方向。原讨论引用了[评论互动能力文档](https://developer.open-douyin.com/docs/resource/zh-CN/interaction/jierushuoming/hudongshuju/pinglunshuju)，并指出消息范围及审批限制需要单独确认，不能假设能读取直播间全部自由评论。

## 6. 历史启动与配置示例

本节用于追溯分享内容。当前命令和模式以运行配置文档为准，尤其不能再按本节推断“启动即自动说话”或“房间号足以接入 B站”。

### 本地启动

在源码导入并核对依赖后，原方案使用以下命令：

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
uvicorn main:app --host 127.0.0.1 --port 8765
```

页面地址约定：

- 舞台：`http://127.0.0.1:8765/`
- 控制台：`http://127.0.0.1:8765/control`

先在控制台发送模拟弹幕，验证入队、生成回复和播放语音：

```json
{
  "user": "小明",
  "text": "你今天怎么又在摸鱼？"
}
```

未配置大模型密钥时，预设文案仅用于验证流程；配置密钥后才调用真实 LLM。

### 大模型与语音

原方案的 `.env` 示例：

```dotenv
LLM_API_KEY=你的API密钥
LLM_BASE_URL=https://你的服务商地址/v1
LLM_MODEL=你的模型名称

AI_NAME=小鱼
TTS_VOICE=zh-CN-XiaoxiaoNeural
```

`小鱼` 是原方案的配置示例，主播名称和人设可在实现时调整。

### Live2D

准备拥有相应使用授权的 Cubism 3/4 模型，将模型及配套文件放入 `models/character/`，并配置模型入口：

```dotenv
LIVE2D_MODEL_URL=/models/character/character.model3.json
```

将所需官方 Cubism Core 文件 `live2dcubismcore.min.js` 放入 `vendor/`。无模型时，原方案以 CSS 演示角色作为聊天和弹幕链路的占位展示。

### B站历史配置已废止

原分享要求安装 bilibili-api-python，并填写 BILI_ROOM_ID。这条路线不再实施；请使用运行配置中的 BILI_MODE=open_live 和相应官方授权配置。平台接入仍需阶段 3 的实际权限与联调。

### OBS

使用浏览器来源加载本地舞台页面，完成画面与音频合成，再配置 B站推流。实际画面尺寸、音频采集、自动播放和持续运行表现需要在设备上联调。

## 7. 实施与验收顺序

按原方案的开发顺序，将每一步的完成条件整理如下：

| 阶段 | 工作内容 | 验收重点 |
| --- | --- | --- |
| 1 | 本地 Agent 与模拟弹幕 | 能主动发言；弹幕能进入队列并触发对应回复；字幕和语音可用；区分演示与真实 LLM 模式 |
| 2 | 真实 Live2D 模型 | 模型与资源能加载；说话时有嘴型表现；表情、动作和待机符合预期 |
| 3 | B站真实弹幕 | 能收到目标房间消息；筛选和回复有效；记录回复延迟与连接稳定性 |
| 4 | OBS 直播联调 | 画面、字幕和声音正常；长时间运行时互动链路保持可用 |

运行设备沿用原方案的 Mac mini 加云端 LLM、云端 TTS 路线。若后续改为本地模型推理，再按实际负载评估设备需求。

角色素材和运行库需满足实际使用场景的授权条件。正式直播阶段纳入 AI 身份披露、内容审核和异常暂停机制。
